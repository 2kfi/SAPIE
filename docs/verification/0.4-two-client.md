# 0.4 two-client verification (M13-a)

This file records commands run on 2026-11-20 and 2026-11-21 in worktree `sapie-r21-m13fix`.
It is evidence, not a real game test. See `0.4-morning-gate.md` for the MW2 2009 run the user
still has to do.

Three separate runs contribute evidence. They are not the same run and must not be read as one:

1. `tools/harness` runs the Go server packages in-process with two raw Go TCP clients. This proves
   server login, ID assignment, DB friendships, presence, invite routing, lobby create and join,
   stats and achievement persistence. It does not exercise the C++ `steam_api` library or a real
   `sapie-server` process.
2. `sapie_login_smoke` runs the C++ library against its own in-process stub server. This proves
   library-side login, mirror, callbacks and stats. It does not talk to the Go server.
3. `live_two_client` runs two C++ processes against a real `sapie-server` with a temp SQLite DB.
   It proves real C++ login, server-assigned IDs, DB friendships, presence, invite callback,
   joined lobby with two members on both sides, stats response and achievement persistence.
   The baseline run failed; the fixed rerun passed. They are shown separately below.

No PASS line below is inferred. Each one is copied from a command output preserved under `out/`.
That directory is gitignored. The final fix evidence is in `out/m13fix/final/`.

The baseline host then exited with SIGSEGV inside `libsteam_api.so`. A gdb backtrace shows the copy
frame where teardown surfaced:

```text
#0  google::protobuf::internal::InternalMetadata::DoMergeFrom<std::string>
#1  Friend::Friend(google::protobuf::Arena*, Friend const&)
#2  Steam_Friends::steam_friends_run_every_runcb(void*)
#3  background_thread(Steam_Client*)
```

Root cause and fix:

- Join failure: `send_owner_packet()` only worked when the guest had a local `Lobby` snapshot.
  The server routes lobby frames only to members, so an invited guest never received the snapshot
  needed to address its JOIN. The shared helper now falls back to
  `sapie::local_mirror().friend_lobbies()` and addresses the JOIN to the friend whose presence
  advertises that lobby.
- SIGSEGV: the harness exited without `SteamAPI_Shutdown()`, leaving the library background thread
  alive while protobuf statics were destroyed. The `Friend` copy was the teardown symptom, not a
  live two-client data race. The harness now registers `SteamAPI_Shutdown()` with `atexit` right
  after `SteamAPI_ManualDispatch_Init()`.

No server, proto or schema source was changed for either fix.
